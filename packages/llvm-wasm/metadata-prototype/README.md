# Slot metadata compiler prototype

Standalone experiment only; no product integration, real loader, or GC integration. This variant uses pinned upstream `jitEmitScript` with `AotEmit`, never `src/wasm`. A separate disposable checkout (`.work/xyo-ir-metadata`) and output tree (`.work/metadata-build`) avoid source/artifact races with the original IR-only prototype. The checked-in wrapper pair in this directory is copied into `src/jit` of that disposable checkout; `prototype/llvm19-compat.patch` is applied only there. `CMakeLists.txt` excludes upstream `src/wasm` and links the LLVM 19.1.7 Wasm archives read-only. The native codegen and GC implementation are not modified.

## API and safety

`xyo_browser_ir_metadata(result)` returns a borrowed, NUL-terminated UTF-8 JSON string, valid only until `xyo_browser_ir_destroy(result)`; it is empty on failure. Metadata v1 contains:

- `targetIndex` indexes compiler Runtime targets in their loaded order; do not assume the same index identifies the same target in another project/runtime. Bind to project and generation independently.
- `targetTriple`, exact LLVM `dataLayout` string.
- `slots` are in AotEmit order: `kind` is upstream enum number (0 VarId, 3 StrLit), `global` is the IR name, `keyHex` encodes **every raw key byte** using lowercase hexadecimal, preserving embedded NUL. StrLit is native `char16_t` bytes on the target compiler (wasm32 little-endian UTF-16, no trailing terminator); VarId is its original byte string. No decoding or C-string conversion of StrLit bytes is safe.
- `abiDescriptor` is an explicit versioned string of target/LLVM layout, **selected only** compile-time sizeof, alignof, and offsetof values, the NaN-boxing tag constants (`tag_base/str/color/nan/false/true/emptystr/undefined/ptrmask`), and the recorded `helper_xyo_varslot_init` signature, as implemented in `descriptor`; `abiFingerprintFNV1a64` is the lowercase 16-digit FNV-1a 64-bit hash over its UTF-8 bytes. It is diagnostic, not cryptographic, not exhaustive, and **does not prove ABI compatibility or authorize execution** (a same-layout/different-tag rebuild now mismatches instead of silently validating). Runtime must independently validate its own ABI, SDK/compiler/features/configuration, provenance and lifecycle. No raw compiler pointer is serialized. `keyHex`/metadata are data, never trusted code.

The wrapper keeps a strict single green-flag / straight-line set/change chain (up to 8 blocks) over numeric shadows / no-yield / allowed-slot subset (each block `data_setvariableto` or `data_changevariableby` with a numeric shadow; `change` lowers inline and needs only the `xyo_to_num` helper beyond `xyo_varslot_init`, both recorded in the descriptor), and additionally requires exactly one script overall (matching the real-host gate), rejects variable ids/names containing NUL (they would truncate as C strings / NUL-terminated UTF-16 globals), and runs a strict fail-closed ZIP preflight before `loadSb3File`: EOCD scan in the same window as the loader, at most 4096 entries, stored/deflate methods only, bounded name lengths, no duplicate names, per-entry uncompressed size capped at 16 MiB, total capped at 64 MiB, and `project.json` required. This bounds the loader's `resize(uncompressedSize)` so a patched multi-GiB central-directory size is rejected without allocating. A post-emit check also rejects VarId slot keys containing NUL. Target layout mismatch, GC rooting, stale project IDs, dynamic linking and target runtime compatibility are not solved by metadata. In particular StrLit must be allocated/rooted with the real runtime's GC, not turned into a compiler-process pointer. The wasm32 pointer-stride fix (`llvm-context-pointer-stride.patch`: `ctxPtr` GEP over `ptr` instead of `i64`, so the stride follows the module DataLayout) is applied in the disposable build checkout only, never to shared upstream. The proven single fixture does not exercise `ctxPtr`, so its IR, slots, and fingerprint are byte-identical with and without the fix; `llvm_ctx_stride_test.py` passes against this checkout (correct native/wasm32 reads plus a negative control showing the old `i64` GEP misreads on wasm32). General `ctxPtr` code paths remain unverified for execution. Do not use this metadata to run generated code in a real host.

## Reproduction

Build using `emcmake cmake -G Ninja -S packages/llvm-wasm/metadata-prototype -B packages/llvm-wasm/.work/metadata-build -DXYO_SOURCE=$PWD/packages/llvm-wasm/.work/xyo-ir-metadata -DLLVM_DIR=$PWD/packages/xyo-cpp-wasm/.work/llvm19-proof/wasm/lib/cmake/llvm -DCMAKE_BUILD_TYPE=MinSizeRel`, then build target `xyo_browser_ir`. Ensure tools/SDK are in PATH. For CPU-heavy operations prefix with `taskset -c 0-3,8-11 env CMAKE_BUILD_PARALLEL_LEVEL=4` on the current host; coordinate with other build jobs. Run `taskset -c 0-3,8-11 env CMAKE_BUILD_PARALLEL_LEVEL=4 bash packages/llvm-wasm/metadata-prototype/test.sh` after the build. This uses actual SB3 fixtures, real LLVM-in-Wasm and no generated-code execution. The isolated Wasm build and Node test passed: stage index 0 gives StrLit `34003200` and VarId `76`; sprite index 1 gives StrLit `41000000e90034d81edd` (embedded NUL, non-ASCII and surrogate pair) and VarId `76e99baa`. The test checks exact kind/global/key bytes, IR slot globals, target index, layout, descriptor FNV recomputation, tag constants, helper signature, and failure output. Descriptor fingerprint is `2749f0107810386f`. This does not test real-host integration or GC.

Tested artifact SHA-256: `xyo_browser_ir.js` `52d6e83b102c4a89331b7380e13aaad150b2e804b20245d6b6f957eb4338801a`; `xyo_browser_ir.wasm` `1c436f0044c8bab0b9f201fa9549e392e70eeafeb2b325833b632015da659e28` (stride fix, tag/helper descriptor, and straight-line set/change chains up to 8 blocks included; loader glue unchanged). These identify this build, not a reproducible or trusted build guarantee. Negative fixtures (`nul-id`, `nul-name`, `zip-bomb` under `.work/metadata-fixtures`) are rejected before codegen/allocation with explicit errors. `test.sh` additionally runs a deterministic 20-fixture malformed-ZIP battery (`make-zip-fuzz.py` → `.work/metadata-fixtures/fuzz/`, checked by `test-zip-preflight.cjs`): truncations at structural boundaries, corrupt EOCD, zero/absurd entry counts, unsupported method, stored size mismatch, duplicate entry, empty/overrunning names, out-of-range local offset, and uncompressed sizes just over the 16 MiB cap plus `0xFFFFFFFF`. All are rejected fail-closed with no IR/metadata leakage and no crash or hang; a legitimate stored-method archive (`stored-valid.sb3`) is accepted with byte-identical IR/metadata to the deflated original. The editor package owns a test-only Brave Worker integration of this same compiler (`packages/editor/test/llvm-compiler-worker.browser.test.ts`, opt in with `XYO_LLVM_COMPILER_BROWSER=1`): it generates the SB3 fixtures inline, serves the built compiler into a real Worker, and asserts the valid IR/metadata plus NUL-id and garbage rejection. A second test in the same file extends the chain editor-side: SB3 → IR → real browser llc/LLD pipeline → shared side module with the exact six-import allowlist, asserting the side exports and slot metadata. Linking only; no host instantiation, no execution. A third test completes the chain editor-side: the side module is dlopened into the real xyo runtime hosted in the same browser Worker, bound from compiler metadata, invoked, and the variable is read back after an explicit GC (NaN-boxed string tag plus UTF-16 "42" asserted; exact heap addresses vary per run). The execution runs twice with a fresh Worker each time, mirroring green-flag run-teardown-run with no cross-contamination. Still test-only with the single exact fixture; no product code or backend selection is involved. A fourth test in the same file drives the whole green-flag flow end to end: admission first, then LLVM compile+link+execute for the admitted set/change/chain/two-variable fixtures (asserting the exact `0x4045000000000000` and `0x4036000000000000` results and both `"10"`/`"20"` strings) or a no-execution fallback for the unadmitted wait fixture. A fifth test drives the real product backend (`packages/editor/src/lib/llvm-backend.ts`) with the real worker runner (`packages/editor/src/lib/llvm-runner.ts` + `llvm-runner.worker.ts`) in a real browser: a mixed project whose admitted change runs once on LLVM while unadmitted motion runs inside the wrapped VM. The backend is registered in the app (`packages/editor/src/lib/register-xyo.ts`, label 実験的) with artifacts packed by `packages/editor/scripts/pack-llvm-artifacts.mjs` into `public/llvm-artifacts` and served from `/llvm-artifacts`; without them `load()` rejects and the app falls back to the built-in VM. A sixth, app-level test boots the built editor and clicks a real green flag on an admitted project, asserting the LLVM-computed value, the motion side effect, the absence of any legacy xyo worker protocol, and that only `/llvm-artifacts` Wasm is fetched. Two integration lessons are pinned: the wrapper deliberately omits the scratch worker flag so the app drives its green flag and stepping (with it, the app routes execution to its own runtime worker instead, silently bypassing the wrapper while it holds the split project), and green flag waits for any in-flight load-time build instead of silently skipping admitted scripts. The runner is two-phase (build once at load, instantiate+invoke per flag) and the backend seeds each run from live variable values, so reflag accumulates exactly like the built-in VM (42 then 84 in the test). The pipeline allowlist is a permission ceiling (subset match) so linker DCE may drop unused imports; unknown imports still fail closed. The flow orchestration itself is a shared product-importable module (`packages/llvm-wasm/src/flow.ts`, unit-tested with fake stages in `packages/llvm-wasm/tests/flow.test.ts`) returning every bound variable; the browser Worker only supplies the real-artifact stage implementations. A pure commit-back module (`packages/llvm-wasm/src/commit.ts`, unit-tested in `packages/llvm-wasm/tests/commit.test.ts`) patches the executed scalars into loadable project variable records, failing closed on unknown, ambiguous or unrepresentable values; the browser flow test asserts the committed projects (`"42"`, `42`, `22`, `"10"`/`"20"`). For general multi-script projects, a splitter (`packages/llvm-wasm/src/split.ts`, unit-tested in `packages/llvm-wasm/tests/split.test.ts`) extracts each admitted green-flag hat plus its chain into a minimal single-script project the existing flow compiles as-is, leaving every other block untouched for the built-in VM; shared explicit-shadow blocks are deliberately left in place. A seeded integration fuzz (`packages/editor/test/llvm-split-integration.test.ts`, headless) closes the loop on random multi-script projects: every admitted synthesis must pass the whole-project admission gate and compile in the real metadata compiler, while the remainder must load and step in the real built-in VM without throwing. The experimental product backend (`packages/editor/src/lib/llvm-backend.ts`, unit-tested with a fake runner in `packages/editor/test/llvm-backend.test.ts`) implements exactly that wrapper contract around a real ScratchVM: admitted scripts run on LLVM and commit back via `setVariableValue`, the rest runs inside, failures never throw green flag, and disposal suppresses late commits. The built-in VM side of the differential is pinned headlessly by `packages/editor/test/llvm-builtin-differential.test.ts` (same fixture shape green-flags to a value stringifying to `"42"`, including across reflag), so the LLVM chain's UTF-16 `"42"` and the reference VM agree on project semantics. Routing for a future backend is prepared as a pure function (`packages/llvm-wasm/src/admission.ts`, unit-tested in `packages/llvm-wasm/tests/admission.test.ts`): it admits straight-line set/change chains up to 8 blocks toward LLVM and sends everything else to the built-in VM fallback. It operates on decoded project JSON only; raw SB3 bytes must still go through the compiler, whose ZIP preflight rejects malformed archives before parsing. Verified against every real fixture: simple/binary/change/valid route `llvm`; wait/two-hats/nul-id/nul-name route `fallback` with matching reasons. `packages/llvm-wasm/tests/admission-fuzz.ts` (seeded, run explicitly with `bun`, not part of `bun test`) differentially fuzzes the router against the real compiler: every project the router sends to LLVM must compile (2000 cases, 35 routed, 0 over-approximations at last run); the compiler remains the authority and re-validates everything. Host-to-editor value mapping is a pure function (`packages/llvm-wasm/src/host-value.ts`, unit-tested): NaN-boxed doubles/bools/empty string, heap strings via an explicit reader (null when unreadable), color payloads as numbers, and null for undefined or unknown tags — including the exact `0x4045000000000000` bits the real runtime produced for the change fixture.
