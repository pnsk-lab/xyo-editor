# Independent Emscripten dynamic-linking proof

This is an isolated experiment, **not an xyo loader or a security sandbox**. It does not use the xyo Wasm emitter or modify the shared LLVM build tree. `side.ll` is handwritten. The side object and shared Wasm are generated by the existing **Wasm builds** of LLVM 19 llc and LLD, executing under Node; the C++ host is built by the installed real Emscripten SDK 6.0.12. The host uses `MAIN_MODULE=2`, `dlopen` and `dlsym`, not a synthetic JS import object.

## Reproduce

From the repository root, with the existing SDK and Wasm LLVM tools at the paths in `run.sh`:

```sh
taskset -c 0-3 bash packages/llvm-wasm/real-loader/run.sh
taskset -c 0-3 bash packages/llvm-wasm/real-loader/run-browser.sh
```

The first command builds and runs the Node positive tests and a separate-process negative test. The second reuses those side Wasm files, builds a worker-target host, and runs it in headless Brave (`BROWSER` may override the executable). Build outputs, browser profiles, logs, and `EM_CACHE` are contained in `packages/llvm-wasm/.work/real-loader/`; sources remain in `real-loader/`. Previously generated source-directory artifacts are ignored and left untouched. Initial cache population can be expensive. `--allow-undefined` is necessary for a dynamic side module; it does not validate its host ABI. LLD warns that shared libraries are not yet stable.

## Observed results

* Node and Brave Worker: real `dlopen`, exported entry lookup, missing module/symbol rejection, host function resolution, side static data mutation, relocated function pointer and `call_indirect`, duplicate open and callback use after one close, and final close all pass. The callback observes the side module's updated data. This exercises runtime relocation/table/memory behavior, not just Wasm validation.
* Node `--expose-gc`: five forced JS collections while the handle remains held, followed by a successful callback. Browser has no exposed GC hook and explicitly skips this check. This does **not** prove arbitrary xyo object/slot GC rooting or post-unload safety.
* A second side module imports a nonexistent function. In this SDK/configuration, `RTLD_NOW` **does not reject it**: `dlopen` and `dlsym` succeed, and invocation aborts on the unresolved symbol. The test runs in a separate process so the abort cannot poison the positive run. No conclusion is made about all Emscripten versions or non-function symbols.
* `dlclose` success is not proof that code/table entries were unloaded, reused, or that stale pointers trap. Never invoke an entry or callback after its owning lifetime ends.

## Minimum safe integration boundary

1. Treat module bytes as fully trusted native-equivalent code: side code shares main memory and host privileges. A Wasm import allowlist and size limits reduce accidents but do **not** sandbox malicious code; use a separately isolated runtime for untrusted programs. Validate binary, ABI version, exact import names/kinds/signatures, requested capabilities, limits and entry exports before loading. Enforce a manifest mapping each permitted unresolved function/data import to a known-live host export, rather than trusting `RTLD_NOW`. `WebAssembly.Module.imports` alone does not provide function signatures or prove runtime symbol resolution; use a proper Wasm/type/dylink parser and host export registry.
2. Build the real host with `-sMAIN_MODULE=2`; preserve every needed host symbol explicitly (`EMSCRIPTEN_KEEPALIVE`, `EXPORTED_FUNCTIONS`, or the appropriate Emscripten mechanism). Build PIC side objects via `llc -mtriple=wasm32-unknown-emscripten -relocation-model=pic -filetype=obj`, then `lld -flavor wasm --shared --allow-undefined --export=<entry>`. Emscripten owns dynamic memory allocation, `__memory_base`/`__table_base`, relocation and GOT, table slots, symbol resolution and initialization: do not instantiate this dylink module independently or invent these values. Version pin the SDK/runtime and verify the ABI after upgrades.
3. For real xyo integration, establish which host functions and `GOT.mem` data symbols (including `xyo_aot_slot_*`) must be retained/exported, and ensure they denote the actual xyo runtime-owned slots. This sample tests a host function and internal side data/function-pointer relocation, **not** xyo slot identity or xyo variable semantics. Slot address, data layout, alignment and value/GC ownership must be validated against the host implementation.
4. Associate each code entry and callback/table index with an owning module handle and live host/runtime/slot roots. Retain all until asynchronous work and calls drain; invalidate every published entry before final close; do not rely on `dlclose` as revocation or garbage collection. Serialize loading/unloading with invocation, prevent reentrant teardown, and discard all handles when the main runtime terminates. For xyo managed objects, register roots through the real collector's supported API; JS GC of the Wasm instance does not establish native GC safety.
5. Check every operation, verify entry and ABI before publication, and define transactional rollback for failures before exposure. Since unresolved calls may abort the entire runtime, reject them in preflight and run remaining risky validation in a disposable Worker/runtime. A failed or trapped runtime should be retired rather than reused without explicit recovery guarantees.

Node and browser tests run the same small main but different Emscripten host builds. They do not establish production product integration, cross-thread table sharing, thread safety, arbitrary dynamic-library dependency resolution, GC during native callbacks, slot relocation, repeated unload/reload, or malicious-input safety.
