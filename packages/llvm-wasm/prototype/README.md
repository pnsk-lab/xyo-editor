# xyo → LLVM IR standalone prototype (experimental)

**Not product-connected. Browser SB3→LLVM IR→Wasm llc/LLD→side module→strict synthetic-host execution passed for one fixture only; execution against a real xyo runtime and GC is unverified.** The wrapper invokes the pinned native `jitEmitScript` with `AotEmit`, not the upstream `src/wasm` emitter. It accepts exactly one green-flag script and its body must be one variable set with a numeric shadow; it then requires `mayYield == false`, no procedures, and slots only `VarId`/`StrLit`, before `verifyModule` and printing. This is a restrictive IR inspection prototype, not proof of safety for untrusted SB3, or permission to execute the IR. No slot metadata is returned and no object or Wasm module is produced. Other hats are not compiled; multiple green flags are rejected. The input size cap does not bound decompression. The compiler and runtime ABI must match before any execution.

## Files and source isolation

The disposable checkout is `packages/llvm-wasm/.work/xyo-ir-prototype`, pinned at `93c80a4bcc007284cdede0b927ec310145eaa0b5`. The working C API sources are `src/jit/browser_ir_api.cpp` and `.h` inside that checkout; copies in this directory preserve them independently of `.work`. They use an opaque result: `_compile` accepts bytes/length, `_ok`, `_text`, `_error` return status/borrowed NUL-terminated strings, `_destroy` releases ownership. No JS integration exists.

`llvm19-compat.patch` affects only LLVM 19.1.7: upstream's compatibility header assumes `withContextDo` and Triple-based APIs for LLVM >=19; actual 19.1.7 headers use `getLock/getContext` and StringRef. Its Triple branch returns an owning `std::string`, avoiding the dangling StringRef in upstream's older branch. Other versions retain upstream logic and are untested. For a fresh checkout: `git apply --check <patch>` then `git apply <patch>`, and copy the two wrapper files into `src/jit/`. Do not patch the shared upstream checkout.

`CMakeLists.txt` is a separate, preliminary build recipe: upstream `XYO_JIT=OFF` provides its ordinary no-JIT engine (not an emitter); it removes `src/wasm` from the globbed source list and adds native `codegen.cpp`, `parfor.cpp`, and this wrapper. GPU/core/pen/loader and other upstream dependencies remain. It links candidate LLVM components from the configured target LLVM package, never host llvm-config. The current component set linked successfully for this one IR-only executable; it does not establish minimal dependencies or a runtime ABI. `nojit_stub.cpp` is not proof that native helper runtime/loader integration works; generated IR is not executed here.

## Results and next gate

- Actual LLVM 19.1.7 Wasm headers + Emscripten `em++` syntax-check both wrapper and native `codegen.cpp`; `bash packages/llvm-wasm/prototype/check-syntax.sh` reproduces this and checks reverse applicability of the patch against the disposable tree. Forward `git apply --check` against the pinned shared source also passed without applying it. This does not compile/link LLVM libraries or run the wrapper.
- An initial configure requested `find_package(LLVM 19)` and failed because the package's version-compatibility rejected `19`; the recipe now loads the specified config and checks exact `19.1.7`. Isolated Emscripten build and link subsequently succeeded without unresolved-symbol diagnostics. The shared LLVM build directory was only read by this build; another agent concurrently regenerated its Ninja configuration, so exact archive immutability during the link was not independently proven.
- To configure after setting up the disposable checkout and applying the patch, use `emcmake cmake -G Ninja -S packages/llvm-wasm/prototype -B packages/llvm-wasm/.work/prototype-build -DXYO_SOURCE=$PWD/packages/llvm-wasm/.work/xyo-ir-prototype -DLLVM_DIR=$PWD/packages/xyo-cpp-wasm/.work/llvm19-proof/wasm/lib/cmake/llvm`. Ensure SDK/tools are on PATH; prefix CPU-intensive configure/build with `taskset -c 0-3,8-11 env CMAKE_BUILD_PARALLEL_LEVEL=4` and coordinate with the shared LLVM build.
- `taskset -c 0-3,8-11 env CMAKE_BUILD_PARALLEL_LEVEL=4 bash packages/llvm-wasm/prototype/run-smoke.sh` creates actual zipped SB3 fixtures and passes them through the linked LLVM-in-Wasm C ABI in Node. The positive set-variable fixture produces IR; wait and two hats are rejected. The test asserts triple `wasm32-unknown-emscripten`, wasm32 pointer DataLayout, `void @xyo_browser_script(ptr %0)`, two AOT slot globals and loads, and the complete emitted call graph (one call to `xyo_varslot_init`, no indirect calls). This only proves this small fixture; it does not execute generated IR or cover all no-yield cases. `smoke.cjs` intercepts instantiation to access the minified memory export; `.js` is copied to `.cjs` because the workspace treats `.js` as ESM. The same script then invokes LLVM `llc.js` + `llc.wasm` inside Node to emit a PIC relocatable Wasm object; native SDK `llvm-readobj` checks wasm32, linking/reloc.CODE, undefined helper and slot relocations. Neither compiler nor object has been integrated into the product.
- Chrome Worker was separately tested using `browser-smoke.html`, `browser-worker.js`, and `browser-smoke.cjs`: a temporary loopback-only HTTP server served the workspace; headless Google Chrome loaded the actual compiler Wasm in a dedicated Worker and reported valid IR plus rejection of wait/two hats. The Worker itself ran LLVM; generated IR was not executed. For reproduction after building the prototype, run `taskset -c 0-3,8-11 env CMAKE_BUILD_PARALLEL_LEVEL=4 CHROME_BIN=/path/to/chrome node packages/llvm-wasm/prototype/browser-smoke.cjs`. The runner regenerates its fixtures, binds a restricted loopback server on an ephemeral port, and closes it after the test; it resolves playwright-core from the editor package. `BROWSER` or `CHROME_BIN` optionally select a browser; otherwise Playwright's default Chromium executable is used.
- Browser end-to-end test: `taskset -c 0-3,8-11 env CMAKE_BUILD_PARALLEL_LEVEL=4 CHROME_BIN=/path/to/chrome node packages/llvm-wasm/prototype/e2e.cjs`. The test bundles the actual `LLVMPipeline` and worker into a private test directory, uses real SB3 and three separately built Wasm artifacts, and serves only fixture assets on loopback port 0. In headless Chrome, it passed: SB3 → xyo `jitEmitScript` IR (984 bytes) → browser Wasm llc + LLD via pipeline → 673-byte side module → closed-world synthetic host, helper called once, Value bits `0x7ff9000000003450`. The LLD emitted `creating shared libraries, with -shared, is not yet stable`. Imports, exports, exact dylink metadata, layout bounds, helper arguments and GOT/slot offsets are checked before executing this one fixture. This is **not** real xyo runtime, GC, arbitrary project, browser security, or production integration validation.
