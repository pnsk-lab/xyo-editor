# Pen state transplant — design only, production gate CLOSED

This proposal does not implement transplant and its model tests are not evidence of real-worker safety. The experimental sink remains OFF in product. The current snapshot is a visual/data overlay, not resumable state (`src/snapshot.ts`); SB3 does not store runtime pen state. `browser.cpp` load replaces the Runtime, and `XyoRuntimeVM.greenFlag` commits the live snapshot and immediately interrupts the worker before loading an SB3 into another. Persistent canvas pixels alone are insufficient.

## Semantic boundary and payload

At every *committed* worker operation, capture an immutable, versioned pen-state sidecar together with the snapshot and pen command batch, from exactly the same native quiescent boundary. Capture every original target including the stage; never transplant clones. Represent absent lazy state explicitly, distinctly from present defaults. For each present state preserve penDown, color, saturation, brightness, transparency, legacy shade, diameter and the exact RGBA/colorDirty cache needed for subsequent drawing; either transport the lastSetColor cache safely or invalidate it with a proven semantics-preserving sentinel (it is Value bits and MUST NOT transport a dangling string/GC pointer). Restoring penDown must install the native pen movement hook without emitting a point or otherwise executing a block; pen-up must not retain that hook. It must not copy raw pointers or use the pen-down primitive, which emits a point. Validate fields and version natively; preserve valid edge cases rather than silently clamping. Determine actual representable numeric domain and cache validity by differential tests before freezing the format.

Identity must be a host-issued stable editor target ID bound bijectively to an original in both snapshots and the loaded candidate; regenerated xyo IDs and names alone are not stable across rename, duplication, deletion or replacement. Binding must survive SB3 round trip (or use a separately validated load-time mapping) and reject ambiguity. Include project-instance identity, revision, generation, operation sequence and schema in the sidecar envelope. Do not serialize into the project SB3 or expose it as a general execution checkpoint.

## Transaction and linearization

1. On an operation return, worker collects snapshot, batch and complete original sidecar in one result. No callback/reentry. Main thread validates the *entire* bundle including target bijection, sidecar and generation/revision before touching visible state. Apply ink atomically and publish matching snapshot and sidecar as one committed frame; listener exceptions after commit retain that complete frame and fail-stop.
2. A stop/reflag/edit invocation advances the generation synchronously; stale replies, clone state and commands can never update the committed frame. It uses only the last fully committed bundle. The pending operation might already have mutated native state or might never settle: synchronously terminating a worker cannot extract its most recent state. Therefore this scheme is equivalent to Scratch only if the product establishes and tests that the committed boundary is the stop linearization point, or waits for a bounded cooperative quiescence protocol without allowing operations to cross the boundary. If that cannot be established, reject restart and keep product OFF; never silently reset pen state or trust a partial frame.
3. For restart, capture edited SB3 and sidecar under one revision, load into a private candidate, verify project/revision/target bijection, and install all sidecar entries transactionally before greenFlag. Validate all entries and allocate all state before modifying any candidate target. No pen commands emitted during restore. After each asynchronous step recheck generation/revision. A failure or late result destroys candidate, preserves last committed ink and state, reports error, and does not run scripts. Run flag only after successful restore; validate and commit its complete response normally.
4. Project replacement synchronously invalidates epoch, removes saved sidecar and discards pen layer. An ordinary project edit should preserve the state of the *same surviving original objects* and committed ink, but not a deleted-and-recreated target even with the same name; new/duplicated sprites require explicit verified Scratch semantics (including pen state inheritance) and must not inherit by guessed ID/name. If edit notifications provide insufficient pre/post identity or are reordered, reject transplant for that edit rather than resetting or guessing. An edit must not merge an old worker state over the edit. Undo/redo and import are subject to the same identity proof. A replacement notification alone is insufficient to distinguish replacement from ordinary notifications; use proven project-instance identity.
5. Stop and green flag remove clones per Scratch semantics, not their previously committed ink. No cloned pen state can be applied to originals, including clones deleted before the sidecar was produced. Project replacement removes ink; stop/reflag do not clear it. Check actual upstream stop/flag ordering and Scratch reference behavior before implementation; do not assume host commit implies native stop has completed.

## Independent release gates

* Compare Scratch VM, same-runtime xyo and transplanted xyo for pen-down motion after stop/reflag, pen-up, lazy state, hue/saturation/brightness/transparency/legacy shade, diameter, color-cache dirty/clean paths, and no spurious restore dot; include stage and multiple sprites. Verify clone inheritance, clone deletion and old ink pixel equality.
* Actual worker plus adapter/browser tests: delayed/never-returning step, stop/reflag/edit/replacement during every await, reordered responses, duplicate/invalid targets, rename/delete/recreate/duplicate and edits to blocks/assets, simultaneous flag, invalid/non-finite/unknown payload, allocation/restore failure and subsequent operations. Assert atomic ink+snapshot+sidecar, no stale publication, fail-stop and no mutation on rejected candidate. Include forced movement, unsupported stamp/overflow, delivery/overlay/notification failures.
* Validate lifecycle against reference Scratch VM with executable tests, including whether editor-driven operations and clone deletion affect state. Model tests exercise only the intended transaction rules; they cannot establish equivalence to either runtime or prove the current adapter supports those rules.
* Independent review must prove the linearization and edit identity conditions above, plus end-to-end worker transport and native restore. Until every applicable phase is proven safe, product enablement is prohibited.
