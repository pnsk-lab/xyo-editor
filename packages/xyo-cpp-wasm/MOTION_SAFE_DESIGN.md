# Safe flag WASM: isolated motion candidate (design only)

Status: **not implemented or integrated**. This is a proposed, deliberately narrow experiment, not a claim that basic.sb3 now compiles or that its renderer matches Scratch. `safe_*` files are being changed independently; all implementation details below must be reconciled with their current version before use.

## Observable behavior to preserve

The current xyo-cpp interpreter calls `Target::setXY` for each of `motion_changexby` (input `DX`), `motion_setx` (`X`), `motion_changeyby` (`DY`), `motion_sety` (`Y`), and `motion_movesteps` (`STEPS`). Set/change reads the other coordinate as-is; change adds to the current coordinate. Move computes `radians = (M_PI * (90.0 - direction)) / 180.0`, `dx = steps * v8math::cos(radians)`, `dy = steps * v8math::sin(radians)`, then adds each to the current coordinate. Keep this order and the V8-compatible helpers: substituting WASM/JS trigonometry or rearranging operations can differ in the low bits.

`setXY` first returns for stage or dragging (unless force, which these blocks do not use). Otherwise it captures old x/y; **if a renderer is attached, it calls `getFencedPosition` even if fencing is disabled**, passing the fencing flag and drawable ID; it then writes both x and y; invokes `onTargetMoved(this, oldX, oldY, false)` even for identical coordinates; for a runtime, emits visual change and requests redraw if renderer and visible, and calls `requestTargetsUpdate(this)` regardless of visibility. The movement callback can produce pen lines and is not a pure notification. Neither `x` nor `y` is an independent safe output slot. Headless execution skips the renderer fence but not the callback or target update. The browser renderer bridge's fence callback also synchronizes scene state even when fencing is disabled; assuming `fencing == false` means no observable call is wrong. Renderer bounds and fence calculations belong to the installed renderer and can depend on drawable, costume, size, rotation and host state; do not replace them with fixed stage bounds or a cached fence rectangle. The existing Canvas bridge explicitly documents approximate collision/fencing; compare against the same installed renderer, not an idealized clamp.

`setXY` does not reject nonfinite coordinates. Numeric casting, arithmetic overflow, NaN, infinity, signed zero, and existing nonfinite coordinates therefore cannot be silently normalized. For the first experiment conservatively fall back before any side effect if input, relevant coordinates, direction, intermediates or result are nonfinite; check the unused coordinate too. Preserve finite signed zero and exact operation order. These gates restrict optimization, not interpreter behavior.

## Minimal proposed execution boundary

Start with a **single motion statement**, not a batch, with a single accepted pure finite numeric literal input and no variable writes in the compiled region. Compile/evaluate the input in WASM into private staging memory, then after successful invocation and all checks execute the original motion operation exactly once on the host, via its canonical primitive or an equivalent shared core helper which invokes `setXY` (for move, reuse `moveSteps`; for coordinate ops use the same primitive/host operation, not field assignments). This can work with either renderer attachment state because side effects stay in the canonical host operation. Host reads x/y/direction at the same semantic instant as the interpreter, not at green-flag compilation. Stage/dragging behavior must remain as in `setXY`, including evaluation of input before the call.

Never call the renderer or `setXY` during the speculative WASM invoke or preflight. Compilation failure, CSP rejection, nonfinite preflight, failed invoke/trap or injected failure must fall back with **zero** motion side effects. Once the host motion call begins, it is the commit point: never catch an exception/trap and reexecute the interpreter statement. Preserve the interpreter's own exception/lifetime/reentrancy behavior instead. Arbitrary callbacks may mutate runtime, renderer, target, graph, or even target lifetime; do not assume they are pure or retain/dereference unsafe pointers after a callback. Demonstrate that advancing the thread and preserving its glow/cache/stack bookkeeping around this boundary is safe under the same callback/reentrancy assumptions as ordinary interpreter execution; otherwise reject that embedding. Do not claim support for arbitrary destructive reentrancy without a lifetime proof.

Reuse existing green-flag graph revalidation, opcode canonical-primitive identity and flow checks, reporter alias/cache checks, bounded scans and exact continuation bookkeeping. Check both the single statement and its literal. No callback or asynchronous boundary may intervene between the last validation and execution except those already present in the original statement. Only enter after the preceding say has actually completed and the thread is at the candidate block; do not hoist across it or change yields. The existing post-flag search can find chunks after straight-line statements, but its current lowerer only accepts variable statements, so this requires future integration and testing. A pending chunk discarded at a yield must not execute later using stale state.

This narrow candidate only compiles the input expression, while the movement remains a C++ host call. It may have negligible or negative performance; benchmark before broadening. It is nevertheless a safe design direction, not evidence of a speedup. No multi-motion fusion: each callback observes the preceding position and can change future state. No speculative callback journal or final-x/y writeback. Supporting variable writes mixed with motion requires a separate proof of intermediate visibility, aliasing and trap/commit ordering. Supporting more expression inputs requires their complete interpreter evaluation/cast/cache semantics and rollback proof.

## Independent differential test plan before integration

Run identical fresh projects with safe disabled/enabled and compare per-step ordered traces, exact double bits (including -0 where applicable), callback arguments, final state, thread status/stack/glow and renderer/redraw/update events; assert actual compilation/execution on the eligible path, not only equal results. Also compare `looks_say -> motion_movesteps` for the real basic fixture, including compilation counters and bubble state. Test candidate in the middle of a chain with continuation and separately at end; ensure no movement is repeated or skipped.

1. Each of five opcodes; finite literals including negative, fractional, +0/-0; direction cardinal and non-cardinal; boundary values; consecutive moves to ensure one callback per statement. Verify exact V8 helper result, not merely epsilon equality.
2. Detached renderer versus attached renderer with fencing on/off; fake renderer logs fence requests/flag/drawable and modifies both coordinates, including out-of-bounds and oversized/rotated drawable scenarios. Exercise visible/invisible, valid/missing drawable under the host's normal contract, costume/geometry changes between prepare and execution. Include actual browser bridge integration separately because its sync and bounds behavior may differ from a fake.
3. Stage, dragging (including state changed after preparation), unchanged coordinates, onTargetMoved with pen down and pen up, old/new values and force=false; verify callback, visual change, redraw and target-update ordering/count. For callback-driven mutation or reentrancy use only cases supported by the interpreter and compare its traces; unsupported lifetime cases must not be optimized.
4. NaN/infinities from inputs, initial x/y/direction, arithmetic overflow and nonfinite renderer output; verify safe fallback occurs before any effect where gated and preserves the interpreter result. A renderer-produced nonfinite value arises only after commit has begun: do not retrospectively fall back. Add signed-zero checks.
5. CSP rejection, validation failure, stale graph, changed primitive registration, shared reporter/cache contamination, invoke trap and fail-after-invoke: no speculative side effects and exactly one interpreter motion. Include say/yield before the candidate and edits before the candidate executes.
6. Bounded graph/alias scan, malformed or cyclic chain, unsupported reporters, stage/clone/stack-click/monitor eligibility and cleanup/stop cases: assert rejection or exact existing eligibility, no stale module leak. Test input evaluation and stack/cache bookkeeping against the interpreter.
