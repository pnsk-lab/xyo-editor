# SoundBank bridge integration and prototype contracts

`sound_bank_bridge.*` implements the upstream `SoundBankAPI`, but is **not** included in the WASM build or connected to the browser/editor. It uses opaque monotonically increasing per-bridge voice IDs and defers completions until `pump()` after the runtime step, including failed starts and synchronous host callbacks. The host must copy sound bytes/metadata during `start`, and playback completion/failure must call `complete(id)` on the same bridge instance on the runtime thread. IDs are not globally unique: route callbacks with an independently unique runtime/bridge generation, never a recycled raw bridge pointer or voice ID alone. Disable that route before destroying the bridge/runtime. Host stop must tolerate late and duplicate completions.

Required integration ordering:

* Install the bank on each loaded Sprite (clones share Sprite); clear those non-owning pointers before destroying the bank. Keep bank and Runtime alive during all calls. Call `shutdown()` before Runtime destruction or replacement; callbacks from the old generation must then be ignored. `shutdown` cancels voices without resuming stopped scripts.
* Before clone deletion call `forgetTarget(clone)`; before project stop/green flag call `shutdown()` or otherwise invalidate every affected voice before Runtime::stopAll deletes clones. A reused bank requires a new instance after shutdown. Do not rely on comparing a freed Target pointer to detect target reuse.
* Upstream `Thread` has no wait generation. The experimental `patches/wait-generation.patch` instruments the promise-wait entry sites in the pinned upstream, and the adapter requires compilation with `-DXYO_WAIT_GENERATIONS` against the identically patched Runtime; otherwise compilation fails closed. This must be audited again whenever upstream changes. It protects sound completions against a subsequent promise wait, but does not make other subsystems' own stale `resolveWait` callbacks safe, nor does it cover uninstrumented external status writes. Integrators must invalidate before such writes. On runtime stop/clone deletion use the lifecycle hooks above. Upstream retains `ownedThreads` until Runtime destruction, but `threads` may no longer contain them; the pump checks membership and killed/status before touching a wait. This does not make a stale Runtime pointer safe.
* `stop(target, soundId)` stops matching voices; upstream `stopAllSounds` means all voices, regardless of target. The host `stop(id)` contract is **synchronous**: by return it must have removed that voice from future playback/mixing; a host that only enqueues an asynchronous stop is incompatible with this adapter. Already buffered hardware audio may still be audible. Bridge stop resolves sound waits on the next pump, not inside `stop`; target/project destruction instead invalidates them. The pinned SDL implementation similarly removes voices under the audio-device lock inside `stop`/`stopAll`, then resolves waits on its later `update`; this is a source audit, not a physical audio-device test. Host must implement pitch/pan/volume changes via `effects` and decide playback/restart semantics; this bridge does not decode audio or implement browser autoplay handling.

## Experimental browser ABI patch (not applied to production)

`patches/browser-sound-integration.patch` and `browser_sound_bridge.*` are an experimental callback-table integration, not an editor or WebAudio implementation. They require the wait-generation and safe-runtime patches to be built together. The ABI uses never-reused runtime generations plus 64-bit voice tokens, rejects reentrant handle operations during host callbacks, resets voices before stop/clone deletion, and rejects attach/detach while threads exist. Successful project replacement destroys the old bridge before its Runtime; failed loading retains both. The two callback slots in Runtime are exclusively owned while attached. Volume is only passed on start; live volume/pitch/pan, decoding, browser autoplay and playback are not implemented.

**Do not connect the synchronous stop callback across worker `postMessage`.** Returning after merely sending a message would release a wait before main-thread WebAudio actually stopped. Keep audio disabled unless Runtime and audio run together on the same thread with synchronous stop, or redesign the ABI for an explicit asynchronous stop ACK: only ACK after main-thread voice cancellation, then resolve waits; teardown/replacement must invalidate generation and stop old voices before acknowledging/terminating. Shared-memory blocking introduces isolation and deadlock risks and is not implemented. Buffered hardware output can remain audible after stop.

## Experimental asynchronous worker protocol

`async_sound_bank.*` is connected experimentally through the editor worker and WebAudio host: stop changes a voice to `stopping`; a normal completion, wrong generation, or duplicate message cannot resolve it. Only a matching successful stop ACK marks it done for the next `pump()`. A failed ACK or failed stop dispatch makes the entire generation failed; the worker owner must stop stepping immediately, invalidate the generation, arrange cancellation of every host voice, and terminate/discard the Runtime. No waits are resolved on that path. Clone disposal drops all target/thread pointers but keeps a stopping record until ACK so a late stop failure is not lost. The owner must allocate nonzero generations that never repeat across the entire transport and discard old-generation messages. `start` returning false means it is **certain no playback was launched**; ambiguous delivery must instead fail and tear down the whole generation. Host callbacks only enqueue and must not synchronously reenter the bank. `invalidate()` itself does not stop host voices: the owner must invalidate transport routing and cancel them separately. The editor worker transport, wall-clock watchdog, and outer teardown are experimental; they require further compatibility testing. `src/web-audio-host.ts` is the main-thread playback manager used by that transport. It copies bytes, guards generation and voice IDs, and synchronously cancels decoding/active sources; invalidation suppresses old callbacks. Its terminal callback must enqueue rather than reenter the bank, and must not throw. The transport must ACK each stop based on the synchronous `stop()` return, including when completion raced ahead of the stop; terminal reports alone are not stop ACKs. A false stop/invalidation result requires generation failure and teardown, not a successful ACK. The owner must allocate never-reused generations and manage AudioContext creation, autoplay/resume, and disposal. Live effects, complete format compatibility, and production integration remain unimplemented. Mock tests do not establish real browser/device behavior. `async_sound_bank_test.cpp` passes against the patched WASM Runtime with the safe compiler linked; it exercises real sound and ask blocks, early/wrong/duplicate ACK, failure, invalidation and clone late-failure.

### Experimental ACK browser ABI (independent patch)

The production browser C ABI integrates `browser_async_sound.*` as an opt-in poll-only queue; the older `patches/browser-async-sound-integration.patch` remains a historical independent prototype and must not be applied. The build applies `wait-generation-production.patch` after safe-runtime, target-lifetime and question-ID patches; `wait-generation.patch` remains the standalone prototype. After green flag, open audio before stepping. `Start` supplies copied bytes, target and format; `Stop` must receive a generation/id ACK after the host actually stops it. Wrong/early ACKs are ignored. Explicit close and Runtime stop discard queued starts and emit `CancelGeneration`; the host must tombstone that generation, cancel all its voices (including delayed starts), and ACK only after cancellation. Until this ACK, detach, reload, green flag and destruction are rejected. Tick is nonblocking; a stop timeout or failed stop marks failure, stops Runtime and emits cancellation. A cancellation timeout fails closed but cannot safely free the session without a later successful host ACK; host/worker loss needs an outer supervisor teardown. Generation values are unique within one WASM module, so replacement of the whole module needs an additional external epoch. The ABI limits queued commands and outstanding voices to 256, each sound to 8 MiB, total queued sound bytes to 16 MiB, target IDs to 4096 bytes and formats to 256 bytes. On a start limit or dispatch failure, an optional host transport-failure probe immediately latches the bank failed so subsequent starts in the same step are rejected; ordinary start rejection and missing assets remain nonfatal. Once the runtime step returns, the owner fails the generation without resolving waits and queues cancellation. An undrained command times out in ticks; owners must continue ticking even when not stepping and also enforce a wall-clock watchdog. Failure/cancel ACK cannot be guaranteed after worker loss: the independent outer supervisor must cancel all main-thread voices for that worker epoch, including pending starts, without depending on the dead worker. These hooks exclusively occupy Runtime stop/target-removal callbacks.

The browser ABI rejects all synchronous reentry module-wide, including from renderer callbacks and across handles, including question-ID operations. `xyo_browser_audio_session_generation` exposes the attached generation immediately after open (including before the first command) until detach. This is a single-owner-thread guard, not pthread synchronization. All returned pointers, including command bytes and strings, expire contractually at the next browser ABI call: obtain lengths first, then copy each pointer immediately. `browser_async_sound_abi_test.cpp` ran in Node/WASM against an isolated Runtime with both safe-runtime and wait-generation patches: it covers actual sound/stop blocks, early/wrong ACK, successful ACK, timeout, failure, project stop/restart and stale generation, renderer-callback reentry rejection, plus target-removal cancellation via a real Runtime clone. It does not exercise an actual JS worker or WebAudio or verify every wait path. The patches were applied independently of the product build.

The separate `browser_sound_abi_test.cpp` ran against an isolated patched WASM Runtime with the safe compiler enabled: it covers real SB3 loading and sound blocks, failure, stop, duplicate completion, failed/successful replacement, old-generation rejection, destruction and callback reentry. It does not exercise actual JS/WebAudio callbacks or browser ABI clone deletion.

The standalone native test links an isolated patched upstream Runtime and exercises completion, duplicate/late completion, stop, failed start, a manually initiated subsequent wait, explicit wait invalidation, clone disposal, and shutdown. `sound_bank_runtime_blocks_test.cpp` additionally ran natively and in patched Node/WASM: it executes real `sound_playuntildone` and `sensing_askandwait` blocks, checks stale/duplicate completion, stop timing, failure, and clone disposal. It does not validate every wait-entry site or a real browser audio device. Full WASM/browser integration remains necessary; the current adapter alone is not sound compatibility.
